# ConcertMVP

Две независимые реализации сайта Концертного центра «Сириус» на React:

- [Astro + React](https://miggrabbid.github.io/ConcertMVP/astro/)
- [Gatsby + React](https://miggrabbid.github.io/ConcertMVP/getsby/)

Обе версии используют гибридный подход: готовый HTML создаётся во время сборки (SSG), а после загрузки страницы React гидратирует его и включает клиентскую интерактивность (CSR). Сервер во время выполнения не требуется — результат публикуется как набор статических файлов на GitHub Pages.

## Структура репозитория

| Путь | Назначение |
| --- | --- |
| `astro/` | Самостоятельная версия на Astro 5 и React 19 |
| `astro/src/pages/` | Файловые маршруты Astro: главная и динамический маршрут концерта |
| `astro/src/layouts/` | Базовый HTML-layout, SEO-метаданные и JSON-LD |
| `astro/src/app/` | React-приложения, компоненты, хуки, API-слой, mock-данные, i18n, типы и стили |
| `astro/public/` | Статические изображения и шрифты Astro-версии |
| `getsby/` | Самостоятельная версия на Gatsby 5 и React 18. Имя каталога также используется в публичном URL |
| `getsby/src/pages/` | Статические страницы Gatsby, включая главную |
| `getsby/src/templates/` | React-шаблон страницы концерта |
| `getsby/src/app/` | React-приложения и общий прикладной слой, аналогичный Astro-версии |
| `getsby/static/` | Статические изображения и шрифты Gatsby-версии |
| `getsby/gatsby-node.ts` | Создание страниц концертов во время сборки |
| `pages-root/` | Файлы корня итогового сайта GitHub Pages |
| `.github/workflows/deploy-pages.yml` | Проверка, сборка и единая публикация обеих версий |
| `reference-assets/` | Референсы и вспомогательные материалы для визуальной сверки |

В обеих реализациях папка `src/app/` организована одинаково:

| Каталог | Ответственность |
| --- | --- |
| `api/` | Клиентский API-слой на Axios и его mock-адаптер |
| `components/layout/` | Шапка, подвал и общие элементы раскладки |
| `components/sections/` | Секции главной страницы и страницы концерта |
| `components/ui/` | Переиспользуемые UI-компоненты |
| `hooks/` | Загрузка данных, состояние запросов и выбранный язык |
| `i18n/` | Русские и английские переводы интерфейса |
| `mocks/` | Данные главной страницы и концертов для SSG и mock API |
| `types/` | TypeScript-модели данных |
| `styles/` | Общие стили и подключение шрифтов |

## Маршруты

Каждая версия генерирует главную страницу и 18 страниц концертов.

| Страница | Маршрут внутри версии |
| --- | --- |
| Главная | `/` |
| Концерт | `/projects/{projectId}/concerts/{concertId}/` |

При публикации маршруты получают префикс соответствующей версии: `/ConcertMVP/astro/` или `/ConcertMVP/getsby/`.

## SSG и CSR

### Astro

| Область | Режим | Реализация |
| --- | --- | --- |
| Главная страница | SSG | `src/pages/index.astro` формирует HTML из русских mock-данных во время `astro build` |
| Страницы концертов | SSG | `getStaticPaths()` в `src/pages/projects/[projectId]/concerts/[concertId].astro` создаёт отдельный HTML-файл для каждого концерта |
| Layout и SEO | SSG | `BaseLayout.astro` добавляет `title`, description, canonical, Open Graph и JSON-LD события |
| React-интерфейс | SSG + CSR | `HomeApp` и `ConcertPageApp` сначала рендерятся в статический HTML, затем директива `client:load` гидратирует их сразу после загрузки страницы |
| Интерактивность и данные | CSR | На клиенте работают карусель, фильтрация афиши, меню, анимации при прокрутке, смена языка, `localStorage`, повтор запросов и Axios mock API |

Astro сохраняет статическую оболочку и SEO-разметку, но в текущей реализации весь React-интерфейс страницы является одной гидратируемой областью.

### Gatsby

| Область | Режим | Реализация |
| --- | --- | --- |
| Главная страница | SSG | `src/pages/index.tsx` рендерится в HTML во время `gatsby build` с начальными русскими mock-данными |
| Страницы концертов | SSG | `gatsby-node.ts` вызывает `createPage` для каждого концерта и передаёт данные в `src/templates/concert.tsx` через `pageContext` |
| SEO | SSG | Экспорты `Head` создают метаданные, canonical, Open Graph и JSON-LD события во время сборки |
| React-интерфейс | SSG + CSR | Gatsby предварительно рендерит React-страницы, а в браузере автоматически гидратирует всё дерево приложения |
| Интерактивность и данные | CSR | После гидратации работают те же сценарии: карусель, фильтры, меню, анимации, смена языка, `localStorage`, повтор запросов и Axios mock API |

### Граница между SSG и CSR

| Сценарий | Где выполняется |
| --- | --- |
| Построение маршрутов и HTML всех страниц | На этапе сборки (SSG) |
| Начальный контент на русском языке | Встраивается в HTML при SSG |
| SEO-метаданные и структурированные данные концертов | Создаются при SSG |
| Обработчики событий и локальное состояние React | В браузере (CSR) |
| Переключение на английский язык | В браузере; данные запрашиваются из mock API |
| Повторная загрузка данных и состояния loading/error | В браузере (CSR) |

## Сводное сравнение текущих реализаций

Сравнение ниже относится к фактически реализованному коду, а не ко всем возможностям фреймворков. Обе версии создают одинаковые 19 бизнес-страниц, используют один набор данных и практически идентичный React-слой, поэтому различия в основном связаны с маршрутизацией, гидратацией, SEO и сборочной инфраструктурой.

| Критерий | Astro: плюсы | Astro: минусы | Gatsby: плюсы | Gatsby: минусы |
| --- | --- | --- | --- | --- |
| Соответствие задаче MVP | Архитектура хорошо подходит контентному статическому сайту: HTML и SEO создаются заранее, сервер не нужен. | Возможности Astro-компонентов используются только как оболочка вокруг двух крупных React-приложений. | Получается полностью статический React-сайт с тем же функциональным результатом и без runtime-сервера. | Для 19 страниц текущая Gatsby-инфраструктура сложнее, чем требует фактический источник данных. |
| Маршруты и SSG | Файловый маршрут и `getStaticPaths()` находятся рядом; связь URL, данных и шаблона легко проследить. | Подготовка `assetBase` повторяется в двух `.astro`-страницах; при росте числа маршрутов её стоит вынести. | `gatsby-node.ts` централизованно создаёт все страницы концертов; `pageContext` типизирован отдельным интерфейсом. | Один динамический тип страницы распределён между `gatsby-node.ts`, React-шаблоном и типом `ConcertPageContext`, что добавляет связность и шаблонный код. |
| React и гидратация | Гидратация включается явно через `client:load`; в будущем страницу можно разделить на независимые islands и не отправлять React для статичных секций. Используется React 19. | Сейчас `HomeApp` и `ConcertPageApp` целиком являются одной гидратируемой областью, поэтому основное преимущество частичной гидратации ещё не реализовано. | Весь интерфейс остаётся обычным React/TSX-деревом — привычная модель для React-команды. | Gatsby автоматически гидратирует всё дерево и загружает собственный клиентский runtime; отключить JavaScript для отдельных статичных секций в текущей архитектуре нельзя. Используется React 18. |
| Клиентская навигация | Обычные ссылки дают предсказуемую загрузку готового HTML и не требуют клиентского роутера. | Переход между главной и концертом выполняет полную загрузку документа; предзагрузки страниц нет. | Gatsby имеет встроенные средства SPA-навигации и prefetch. | В текущем коде не используется `<Link>`: все внутренние переходы сделаны через `<a>`, поэтому преимущества Gatsby-навигации не задействованы, хотя её runtime всё равно присутствует. |
| SEO и структурированные данные | Один `BaseLayout.astro` централизует canonical, Open Graph, Twitter Card, favicon и JSON-LD, уменьшая риск расхождений между страницами. | Реализация метаданных привязана к Astro-layout; SEO генерируется только для русской версии контента. | Экспорты `Head` формируют SEO при SSG; `siteConfig` централизует имя, описание и публичный URL. | Разметка `<Head>` дублируется в главной странице и шаблоне концерта, поэтому набор тегов может со временем разойтись. Английской SEO-версии также нет. |
| Передача начальных данных | Русские данные попадают в готовый HTML напрямую из mock-модулей; отдельный серверный слой не нужен. | Props всего React-приложения сериализуются в `<astro-island>`, а те же mock-данные и mock API входят в клиентскую сборку. Обновление афиши требует новой сборки. | `pageContext` явно передаёт в шаблон все данные концерта и доступен как в странице, так и в `Head`. | Контекст страницы сериализуется в Gatsby `page-data` в дополнение к HTML; при больших объёмах данных payload и время сборки будут расти. Обновление афиши также требует новой сборки. |
| API-состояния и смена языка | Есть единый типизированный API-слой, отмена запросов через `AbortController`, состояния loading/error/retry и сохранение языка в `localStorage`. | Английский контент загружается только после гидратации; URL и SEO не локализованы. Axios и `axios-mock-adapter` доставляются в браузер даже при статическом источнике данных. | Реализовано то же поведение и те же состояния благодаря практически идентичному прикладному слою. | Ограничения те же: client-only i18n, отсутствие локализованных маршрутов и клиентский mock-адаптер в production-бандле. |
| Базовый путь и GitHub Pages | `PUBLIC_BASE_PATH`, `import.meta.env.BASE_URL` и `Astro.site` покрывают ассеты, маршруты и canonical; конфигурация компактна. | Нужно сохранять единое правило завершающего `/`; сейчас нормализация повторяется на уровне страниц. | `pathPrefix` и флаг `--prefix-paths` являются штатным механизмом Gatsby для публикации в подкаталоге. | Путь задаётся сразу в `gatsby-config.ts`, `GATSBY_ASSET_BASE`, команде сборки и `siteConfig.siteUrl`; их рассинхронизация сломает ссылки, ассеты или canonical. |
| Зависимости и обновления | В текущем `package-lock.json` 566 записей в `packages`; меньше транзитивная поверхность и используется актуальная для проекта связка React 19 / `react-icons` 5. | Обновления Astro, React-интеграции и React нужно проверять совместно; `.astro` добавляет второй тип компонентов рядом с TSX. | Версии React 18 хорошо совместимы с Gatsby 5 и знакомы большинству существующих Gatsby-проектов. | В lock-файле 1382 записи — примерно в 2,4 раза больше, чем у Astro. Используются более старые major-версии React и `react-icons`, а Gatsby приносит крупный набор сборочных зависимостей. |
| Сборка и артефакты | Vite/Astro создаёт статические HTML, CSS и небольшое число целевых ESM-чанков; `astro check` проверяет также `.astro`-файлы. | Из-за цельностраничного island клиентский код React, i18n, Axios, mock API и компоненты всё равно попадает в сборку. | Gatsby автоматически создаёт HTML, `page-data`, runtime и чанки страниц; `tsc --noEmit` отдельно проверяет TypeScript. | Артефакт содержит дополнительные Gatsby/webpack runtime-чанки, служебные JSON и source maps; сборочная поверхность заметно больше. |
| Работа с изображениями и шрифтами | Простые публичные пути удобны для точного переноса готовых ассетов и не требуют дополнительной конфигурации. | Не используются `astro:assets` и оптимизация изображений; исходные размеры и форматы переносятся в публикацию как есть. | Каталог `static` так же просто сохраняет исходные URL и файлы. | Не используются `gatsby-plugin-image`, GraphQL-трансформации и responsive-варианты, то есть сильная сторона Gatsby для медиаконтента остаётся невостребованной. |
| Экосистема и дальнейший рост | Хорошая база для контентного сайта, где большинство блоков можно оставить статичными, а интерактивность изолировать. Можно постепенно переносить статичные React-секции в `.astro`. | При сохранении цельного React-приложения выигрыш Astro будет ограничен; команде потребуется знание и Astro, и React. | Может быть оправдан при дальнейшем подключении CMS, Gatsby Data Layer, GraphQL и профильных плагинов. | Сейчас `plugins: []`, GraphQL и Gatsby Data Layer не используются, поэтому проект оплачивает сложность экосистемы, не получая её главных преимуществ. |
| Поддерживаемость прикладного кода | API, hooks, components, mocks, i18n и types разделены по ответственности; Astro-специфичный код сосредоточен в pages/layout. | `astro/src/app` является отдельной копией общего слоя, поэтому исправления приходится синхронизировать вручную. | Gatsby-специфичный код в основном ограничен pages, template, config и `gatsby-node.ts`; React-разработчику не требуется новый шаблонный синтаксис. | `getsby/src/app` дублирует Astro-версию; дополнительные `React`-импорты и разные major-версии зависимостей затрудняют автоматическое переиспользование. |
| Контроль качества | Есть строгий TypeScript и отдельная команда `npm run check`. | Нет lint-скрипта, unit/integration-тестов и автоматической accessibility-проверки. | Есть строгий TypeScript и отдельная команда `npm run typecheck`. | Также отсутствуют lint, тесты и accessibility-проверки; Gatsby-специфичное создание страниц проверяется в основном только полной сборкой. |

### Общие сильные стороны и технический долг

| Общие сильные стороны | Общие ограничения и технический долг |
| --- | --- |
| Функциональный и визуальный паритет упрощает честное сравнение фреймворков. | Прикладной слой, стили, mock-данные и ассеты физически продублированы в двух пакетах, что нарушает DRY и повышает стоимость каждого изменения. |
| Готовый HTML, метаданные и JSON-LD доступны до выполнения JavaScript. | Обе версии гидратируют почти всю страницу, хотя значительная часть контента статична. |
| Компоненты, API, hooks, types и mocks разделены по ответственности; запросы поддерживают отмену и повтор. | Mock API и его данные попадают в клиентский код; перед production-интеграцией потребуется заменить адаптер реальным источником и определить стратегию обновления SSG. |
| Статический результат можно недорого и предсказуемо публиковать на GitHub Pages. | Нет автоматических тестов, lint и проверки доступности; изображения не проходят framework-level оптимизацию. |

### Вывод

Для текущего MVP рациональнее выглядит **Astro**: он решает ту же задачу с более компактной конфигурацией и деревом зависимостей, централизует SEO и оставляет прямой путь к уменьшению JavaScript через разделение страницы на islands. Следующий полезный шаг для этой версии — гидратировать только интерактивные блоки, а статичные секции перенести в Astro-компоненты.

**Gatsby** становится предпочтительнее, если проекту действительно понадобятся Gatsby Data Layer, GraphQL, CMS-плагины, встроенная клиентская навигация или единая React-only модель для большой команды. В текущем виде эти возможности почти не используются, поэтому дополнительная инфраструктура не даёт сопоставимой практической выгоды.
