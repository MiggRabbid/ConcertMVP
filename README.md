# ConcertMVP

Две независимые реализации сайта Концертного центра «Сириус» на React:

- [Astro + React](https://miggrabbid.github.io/ConcertMVP/astro/)
- [Gatsby + React](https://miggrabbid.github.io/ConcertMVP/getsby/)

Обе версии используют гибридный подход: готовый HTML создаётся во время сборки (SSG), а после загрузки страницы React гидратирует его и включает клиентскую интерактивность (CSR). Сервер во время выполнения не требуется — результат публикуется как набор статических файлов на GitHub Pages.

## Структура репозитория

| Путь | Назначение |
| --- | --- |
| `astro/` | Самостоятельная версия на Astro 5 и React 19 |
| `astro/src/pages/` | Файловые маршруты Astro: главная и динамический маршрут концерта |
| `astro/src/layouts/` | Базовый HTML-layout, SEO-метаданные и JSON-LD |
| `astro/src/app/` | React-приложения, компоненты, хуки, API-слой, mock-данные, i18n, типы и стили |
| `astro/public/` | Статические изображения и шрифты Astro-версии |
| `getsby/` | Самостоятельная версия на Gatsby 5 и React 18. Имя каталога также используется в публичном URL |
| `getsby/src/pages/` | Статические страницы Gatsby, включая главную |
| `getsby/src/templates/` | React-шаблон страницы концерта |
| `getsby/src/app/` | React-приложения и общий прикладной слой, аналогичный Astro-версии |
| `getsby/static/` | Статические изображения и шрифты Gatsby-версии |
| `getsby/gatsby-node.ts` | Создание страниц концертов во время сборки |
| `pages-root/` | Файлы корня итогового сайта GitHub Pages |
| `.github/workflows/deploy-pages.yml` | Проверка, сборка и единая публикация обеих версий |
| `reference-assets/` | Референсы и вспомогательные материалы для визуальной сверки |

В обеих реализациях папка `src/app/` организована одинаково:

| Каталог | Ответственность |
| --- | --- |
| `api/` | Клиентский API-слой на Axios и его mock-адаптер |
| `components/layout/` | Шапка, подвал и общие элементы раскладки |
| `components/sections/` | Секции главной страницы и страницы концерта |
| `components/ui/` | Переиспользуемые UI-компоненты |
| `hooks/` | Загрузка данных, состояние запросов и выбранный язык |
| `i18n/` | Русские и английские переводы интерфейса |
| `mocks/` | Данные главной страницы и концертов для SSG и mock API |
| `types/` | TypeScript-модели данных |
| `styles/` | Общие стили и подключение шрифтов |

## Маршруты

Каждая версия генерирует главную страницу и 18 страниц концертов.

| Страница | Маршрут внутри версии |
| --- | --- |
| Главная | `/` |
| Концерт | `/projects/{projectId}/concerts/{concertId}/` |

При публикации маршруты получают префикс соответствующей версии: `/ConcertMVP/astro/` или `/ConcertMVP/getsby/`.

## SSG и CSR

### Astro

| Область | Режим | Реализация |
| --- | --- | --- |
| Главная страница | SSG | `src/pages/index.astro` формирует HTML из русских mock-данных во время `astro build` |
| Страницы концертов | SSG | `getStaticPaths()` в `src/pages/projects/[projectId]/concerts/[concertId].astro` создаёт отдельный HTML-файл для каждого концерта |
| Layout и SEO | SSG | `BaseLayout.astro` добавляет `title`, description, canonical, Open Graph и JSON-LD события |
| React-интерфейс | SSG + CSR | `HomeApp` и `ConcertPageApp` сначала рендерятся в статический HTML, затем директива `client:load` гидратирует их сразу после загрузки страницы |
| Интерактивность и данные | CSR | На клиенте работают карусель, фильтрация афиши, меню, анимации при прокрутке, смена языка, `localStorage`, повтор запросов и Axios mock API |

Astro сохраняет статическую оболочку и SEO-разметку, но в текущей реализации весь React-интерфейс страницы является одной гидратируемой областью.

### Gatsby

| Область | Режим | Реализация |
| --- | --- | --- |
| Главная страница | SSG | `src/pages/index.tsx` рендерится в HTML во время `gatsby build` с начальными русскими mock-данными |
| Страницы концертов | SSG | `gatsby-node.ts` вызывает `createPage` для каждого концерта и передаёт данные в `src/templates/concert.tsx` через `pageContext` |
| SEO | SSG | Экспорты `Head` создают метаданные, canonical, Open Graph и JSON-LD события во время сборки |
| React-интерфейс | SSG + CSR | Gatsby предварительно рендерит React-страницы, а в браузере автоматически гидратирует всё дерево приложения |
| Интерактивность и данные | CSR | После гидратации работают те же сценарии: карусель, фильтры, меню, анимации, смена языка, `localStorage`, повтор запросов и Axios mock API |

### Граница между SSG и CSR

| Сценарий | Где выполняется |
| --- | --- |
| Построение маршрутов и HTML всех страниц | На этапе сборки (SSG) |
| Начальный контент на русском языке | Встраивается в HTML при SSG |
| SEO-метаданные и структурированные данные концертов | Создаются при SSG |
| Обработчики событий и локальное состояние React | В браузере (CSR) |
| Переключение на английский язык | В браузере; данные запрашиваются из mock API |
| Повторная загрузка данных и состояния loading/error | В браузере (CSR) |

## Сводное сравнение Astro и Gatsby

Это общее сравнение фреймворков применительно к проекту следующего масштаба:

- около 22–23 страниц с учётом планируемого добавления ещё 3–4 страниц;
- преимущественно контентные страницы и карточки мероприятий;
- умеренная интерактивность: меню, фильтры, карусели, анимации и переключение языка;
- SEO, адаптивность и быстрая первоначальная загрузка важнее поведения полноценного SPA;
- нет сложного личного кабинета, совместного редактирования, real-time-функций и большого глобального клиентского состояния.

Сравнение не зависит от конкретной структуры исходников, набора зависимостей или качества двух реализаций в этом репозитории.

| Критерий | Astro: плюсы | Astro: минусы | Gatsby: плюсы | Gatsby: минусы |
| --- | --- | --- | --- | --- |
| Основная модель | Контент сначала превращается в HTML, а JavaScript подключается только там, где нужна интерактивность. Это естественная модель для сайта данного масштаба. | Подход отличается от привычной архитектуры единого React-приложения и требует понимания границы между статическим HTML и интерактивными islands. | Весь сайт строится как единое React-приложение — модель знакома React-разработчикам и удобна при большом количестве интерактивных компонентов. | Для преимущественно контентного сайта цельное React-дерево и клиентский runtime могут быть избыточны. |
| Производительность в браузере | Astro-компоненты не добавляют клиентский JavaScript по умолчанию; можно независимо выбирать момент загрузки каждого интерактивного блока. | Если обернуть страницу в один большой React-компонент, преимущество частичной гидратации будет почти потеряно. | Gatsby выполняет code splitting, предварительно создаёт HTML и может заранее загружать ресурсы внутренних страниц. | React-гидратация и Gatsby runtime увеличивают базовую стоимость JavaScript даже для относительно статичных страниц. |
| Масштаб в 22–23 страницы | Такое количество страниц без проблем покрывается обычным SSG; добавление ещё 3–4 страниц практически не меняет архитектуру и не создаёт заметной сборочной нагрузки. | Для каждой новой интерактивной области нужно осознанно выбирать способ гидратации и не допускать ненужного дробления интерфейса. | SSG также легко обслужит этот объём; генерация страниц из данных и шаблонов является стандартным сценарием Gatsby. | Преимущества сложного Data Layer на таком объёме могут не компенсировать дополнительную конфигурацию и количество абстракций. |
| Маршрутизация | Простая файловая маршрутизация; статические и динамические маршруты располагаются непосредственно в `src/pages`. | Для поведения сложного SPA может потребоваться клиентский роутер или более крупный framework-компонент. | Файловые страницы сочетаются с программным созданием маршрутов; `<Link>` поддерживает быструю клиентскую навигацию и prefetch. | Программная генерация страниц, Node API и шаблоны сложнее обычной файловой маршрутизации. |
| Интерактивность | React, Vue, Svelte, Solid и другие UI-фреймворки можно подключать точечно и гидратировать через `client:load`, `client:idle` или `client:visible`. | Общее состояние и тесное взаимодействие между независимыми islands организовать сложнее, чем внутри одного React-дерева. | React-состояние, Context, клиентская маршрутизация и сложные связанные сценарии естественно работают в едином дереве. | Даже статичные области обычно становятся частью гидратируемого React-приложения. |
| Контент и данные | Есть типизированные content collections; данные можно получать напрямую из файлов, API или CMS без обязательного GraphQL-слоя. | Для разных CMS может потребоваться самостоятельно выбрать SDK, схему данных и стратегию кеширования либо искать отдельную интеграцию. | GraphQL Data Layer объединяет данные из CMS, файлов, API и баз данных в общую схему; source-плагины скрывают значительную часть интеграционной работы. | GraphQL, схема Gatsby и lifecycle API повышают порог входа и могут быть неоправданными при одном простом источнике данных. |
| SEO | Статический HTML создаётся по умолчанию; layouts позволяют централизовать meta-теги и структурированные данные. | Готового универсального SEO-слоя нет — его нужно спроектировать самостоятельно или подключить интеграцию. | SSG формирует индексируемый HTML; `Head` API и плагины позволяют организовать SEO, sitemap и RSS. | SEO часто зависит от качества выбранных плагинов и принятых в проекте соглашений. |
| Изображения | `astro:assets` поддерживает оптимизацию, responsive-изображения и генерацию подходящих форматов без обязательного GraphQL. | Возможности обработки зависят от типа источника и выбранного deployment-адаптера; для удалённых изображений нужна корректная конфигурация. | `gatsby-plugin-image` предоставляет зрелый конвейер responsive-изображений, placeholder-эффекты и интеграцию с CMS через Data Layer. | Обработка изображений добавляет зависимости и способна заметно увеличить время и потребление памяти при сборке. |
| Режимы рендеринга | По умолчанию используется SSG; отдельные маршруты можно перевести на on-demand SSR, сохранив остальные статическими. | Для SSR необходим адаптер конкретной платформы, а доступные возможности могут различаться между адаптерами. | Можно выбирать SSG, SSR или DSG на уровне страниц; DSG полезен для очень крупных наборов редко посещаемых страниц. | SSR и DSG требуют совместимой серверной платформы; для 22–23 страниц DSG практической пользы почти не даёт. |
| Сборка и CI | Для небольшого контентного сайта сборка обычно остаётся простой: Astro генерирует HTML и собирает только явно подключённый клиентский код. | Производительность зависит от дисциплины: крупные islands и тяжёлые UI-зависимости способны увеличить бандл независимо от фреймворка. | Gatsby имеет развитый build pipeline, кеширование, обработку данных, страниц и изображений. | С ростом контента, GraphQL-запросов, плагинов и обработки изображений сборка становится тяжелее; Gatsby отдельно документирует необходимость её оптимизации. |
| Экосистема | Можно использовать npm-пакеты и компоненты нескольких UI-фреймворков; архитектура не привязывает проект только к React. | Экосистема готовых CMS-интеграций и высокоуровневых плагинов менее централизована, поэтому иногда требуется ручная интеграция. | Большая Gatsby-экосистема включает source-плагины, CMS-интеграции, изображения, аналитику, sitemap и другие готовые решения. | Качество и актуальность community-плагинов различаются; обновление Gatsby может потребовать синхронного обновления нескольких интеграций. |
| Команда и поддержка | Удобен, если команда готова разделять статические и интерактивные части и хочет контролировать количество JavaScript. | Нужно освоить синтаксис `.astro`, директивы гидратации и правила взаимодействия Astro с React или другим UI-фреймворком. | Удобен для React-команды: страницы и компоненты остаются в привычной JSX/TSX-модели. | Помимо React необходимо понимать GraphQL, Gatsby Node API, lifecycle API, плагины и особенности сборки. |
| Возможное усложнение продукта | Можно постепенно добавлять islands или переводить отдельные маршруты на SSR, не меняя режим всего сайта. | Если продукт превратится в насыщенное SPA с большим общим состоянием, Astro станет оболочкой вокруг крупного React-приложения и даст меньше преимуществ. | Лучше подготовлен к интерфейсу, где почти каждая страница тесно связана с React-состоянием и клиентской навигацией. | Если развитие останется в пределах нескольких контентных страниц, дополнительная инфраструктура продолжит давать мало практической отдачи. |

### Влияние планируемых 3–4 страниц

Добавление ещё 3–4 страниц аналогичной сложности не является значимым фактором масштабирования ни для Astro, ни для Gatsby. Оба фреймворка без проблем соберут около 22–23 страниц статически. Выбор следует делать по характеру интерфейса и данных, а не по такому количеству маршрутов:

- если новые страницы будут преимущественно контентными с несколькими независимыми интерактивными блоками, сильнее преимущества Astro;
- если страницы станут частью тесно связанного React-интерфейса с общим состоянием, сложной клиентской навигацией и несколькими CMS, сильнее преимущества Gatsby;
- само по себе увеличение с 19 до 22–23 страниц не требует Gatsby Data Layer, GraphQL или DSG.

### Вывод

Для сайта описанного масштаба и сложности предпочтительнее **Astro**: он лучше соответствует content-first архитектуре, позволяет отправлять меньше JavaScript и остаётся достаточно гибким для добавления нескольких новых страниц и интерактивных компонентов.

**Gatsby** стоит выбирать, если важнее единая React-only архитектура либо заранее известно, что проект будет использовать несколько источников данных, GraphQL, Gatsby-плагины, сложное глобальное состояние и интенсивную клиентскую навигацию. При сохранении текущего уровня сложности эти возможности, скорее всего, не окупят дополнительную архитектурную и сборочную сложность.
